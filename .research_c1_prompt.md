# DEEP RESEARCH COMMISSION

## Research Question
What is the complete, detailed prompt engineering framework for implementing GM R.B. Ramesh's Socratic chess teaching method in a large language model (LLM) — specifically, what system prompt architecture, question taxonomy, error diagnosis rules, and session state management are needed to make an AI chat tutor teach chess the way Ramesh teaches (engineered discovery, never giving answers, installing pattern recognition through active problem-solving)?

## Purpose & Context
This research directly feeds into building a chess training webapp (SvelteKit + Stockfish + AI chat streaming) that aims to implement the Grandmaster 60-Minute Protocol — a method for compressing chess expertise transfer into accelerated learning sessions. The entire protocol depends on the AI executing Ramesh's teaching philosophy: "Teaching is NOT transferring information. I never show things. I only ask questions and engineer positions so the student discovers the concept themselves."

The current webapp already has an AI chat (SSE streaming via /chess/learn/chat), Stockfish in a Web Worker, and a chess board. What's missing is the teaching intelligence — the system prompt, question taxonomy, error diagnosis logic, and state management that makes the AI behave like Ramesh rather than like a standard LLM that gives answers.

The audience is a technical founder building this feature. The report must be detailed enough to directly inform system prompt construction, function/tool design, and session state schema.

### Audience
- **Primary**: Technical founder building the AI tutor feature — needs actionable prompt templates, question taxonomies, and decision trees
- **Secondary**: Chess educators evaluating the method
- **Tone**: Precise, technical, evidence-driven, with specific examples of prompt text and interaction patterns
- **Complexity**: Deep — must cover both prompt engineering techniques AND chess pedagogy

### Decision Context
- What system prompt architecture makes an LLM reliably execute Ramesh's method?
- Can it be done with prompt engineering alone, or is a multi-agent architecture needed?
- What session state must be tracked across turns?
- What's the minimum viable prompt that produces Ramesh-like teaching?

## Required Dimensions of Investigation

### 1. Ramesh's Teaching Method — Complete Documentation
- Exact phrasing: "Teaching is NOT transferring information. I just ask questions. I don't tell them 'you are moving the same piece twice.' Then it is just information."
- His 5-level progression from ~1400 FIDE to GM in calculation — what's the curriculum at each level?
- His "in training, I never show things" principle — how does he structure sessions?
- His error taxonomy: what mistakes does he look for? (not making candidate lists, not refuting own ideas, not curious about opponent's defense)
- His concept of "knowing is not doing" — how does he bridge that gap?
- His habit-breaking methodology: what prevents students from doing what they know?
- His process-over-outcome philosophy and how it manifests in teaching interactions
- His specific drills: 1-hour blind calculation, positional sketches, candidate list enforcement
- Sources: Ramesh RB Next Level Chess Part 1+2, ChessBase India 3-part interview, Perpetual Chess EP 488, NIC Podcast #4, Chess.com Olympiad interview, "Improve Your Chess Calculation" book, "Fundamental Chess" book

### 2. Ramesh's Question Taxonomy — Exact Probes
- Identify every specific question Ramesh asks students, categorized by type:
  * Error diagnosis: "Which principle are you breaking?"
  * Success confirmation: "Which principle did you just follow?"
  * Prophylactic: "What does your opponent want?"
  * Discovery: "What changed after that move?"
  * Reflective: "What do you think you did right or wrong?"
  * Depth: "What could be different reasons that prevent you from doing X?"
  * Commitment: "Are you convinced intellectually that this is the right way?"
- What's the decision tree for choosing which question?
- How does he sequence questions across a session?
- How does he know when the student has truly understood vs. just parroting?

### 3. Existing Socratic Tutor Prompt Engineering — State of the Art
- OpenAI's official Socratic Tutor prompt (3 sentences): "You are a tutor that always responds in the Socratic style. You *never* give the student the answer, but always try to ask just the right question to help them learn to think for themselves."
- Khanmigo's approach: Socratic-style AI tutor with scaffolding
- Community prompts: the Socratic Universal Tutor, Socratic Tutor for Mastery, etc.
- Nielsen et al. (2008) question taxonomy for tutoring systems
- The "Socratic Iterative Prompt Engineering" (SIPE) framework (Boussioux et al. 2024)
- Common failure modes: LLMs default to "be helpful = give the answer," need explicit override
- What works: explicit rules against giving answers, modeling correct dialogue, level adaptation
- What doesn't: vague "be Socratic" instructions without concrete examples

### 4. Chess-Specific Socratic Interaction Design
- How to map Ramesh's questions to LLM-generated output based on board position
- Position-dependent question generation: "If user blunders a fork → 'What's the relationship between your knight and my pieces?'"
- Error class to Socratic probe mapping:
  * Missed tactic → "What checks/captures/threats does your opponent have?"
  * Passive move → "Which piece isn't doing anything?"
  * Calculation failure → "Did you make a candidate list before choosing?"
  * Prophylactic neglect → "If you were me, what would you play next?"
  * Planlessness → "What does the position tell you to do?"
- How to integrate Stockfish evaluation into question selection
- How to detect discovery moments (lexical markers, speed changes, accuracy improvements)

### 5. System Prompt Architecture for Ramesh-Style Teaching
- Components needed: role definition, core principles, question templates, error response patterns, session memory requirements
- How to structure the "never give the answer" constraint to survive jailbreak attempts
- How to handle edge cases: user asks directly for answer, user gets frustrated, user gives up
- Personality modeling: Ramesh is demanding but supportive, focuses on effort over results
- The "training should be harder than the game" principle — how to encode difficulty calibration
- Sample system prompt templates for each of Ramesh's 5 levels

### 6. Session State & Memory Requirements
- What must persist across conversation turns: user's Dreyfus stage, patterns installed, errors made this session, current position, current drill phase
- How to serialize this state for context window management
- What to remember across sessions: installed patterns, common error types, learning trajectory
- State transition diagram for a teaching session

### 7. Error Diagnosis from Board + Move
- Given position + user's move + Stockfish evaluation, how to classify error type
- Ramesh's categories: does the error map to his framework?
- How to distinguish tactical error from positional error from strategic error
- How to distinguish "didn't see it" from "saw it but chose wrong"
- Can this be automated or does it require an LLM judgment call?

### 8. Failure Modes & Limitations
- LLMs giving answers despite instructions (the "helpfulness" override)
- LLMs accepting wrong answers and moving on
- LLMs being too easy on the student (Ramesh is demanding)
- LLMs not adapting to the student's level
- LLMs losing track of session context
- Known issues with Khanmigo and other Socratic AI tutors
- How real chess teachers differ from LLM approximations

### 9. Validation & Testing Approaches
- How to test if the prompt actually produces Ramesh-like teaching
- Evaluation criteria: answer rate (should be near 0%), question quality, error diagnosis accuracy, session coherence
- Test positions and expected AI responses
- User satisfaction metrics

### 10. Practical Applications & Implementation Guidance
- Minimum viable prompt (MVP) for a chess Socratic tutor
- Recommended architecture: single LLM + tools (Stockfish eval access) vs. multi-agent
- Context budget: typical token usage per interaction
- Streaming considerations for SSE chat
- Integration with existing /chess/learn/chat endpoint
